3. รถเข้าซ่อมรถเข้าเขตรับบริการและช่องซ่อมเทียบเวลาเข้า-ออกกับ Job Order และสถานะปิดงาน
4. อะไหล่การเคลื่อนย้ายกล่อง/สิ่งของในจุดกำหนดเทียบการเบิกกับ Parts Issue และใบสั่งซ่อม
5. เงินสด/พื้นที่รับชำระการเข้าใช้พื้นที่หรือเหตุการณ์กำหนดเทียบรายการรับชำระกับ POS และรายงานปิดยอด

ทรัพย์สินเครื่องจักรรถ/เครื่องจักรออกจากพื้นที่กำหนดเทียบกับตารางใช้งาน·ใบขออนุญาตเคลื่อนย้าย·ทะเบียนทรัพย์สินใน ERP
คลังผลผลิต/จุดชั่งน้ำหนักการเข้าออกนอกเวลา · น้ำหนักไม่ตรงบัตรน้ำหนักกระทบยอดตรวจนับ ↔ บัญชีใน ERP · ตรวจสิทธิ์ผู้เข้าพื้นที่จัดเก็บ
การขายและการรับชำระรถขนผลผลิตออกโดยไม่มีเอกสารเทียบคำสั่งขาย·ใบส่งของ·หลักฐานชั่งน้ำหนัก·รายการรับชำระ — ออกไม่มีบิล = Case ระดับสูง
แรงงานภาคสนามการเข้าทำงานในเขตเพาะปลูกตามช่วงเวลาเทียบบันทึกงานกับชั่วโมงที่รายงาน (aggregate ไม่ระบุตัวบุคคล) + ความสอดคล้องสัญญาจ้าง/กฎหมายแรงงาน
กฎหมาย·ภาษี·Compliance (LCT)—ทะเบียนหน้าที่ตามกฎหมาย: การยื่น/ชำระ·ใบอนุญาต·สิทธิที่ดิน·มาตรฐานสารตกค้าง — GAT LCT Reviewer เป็นผู้ตรวจหลัก
ตัวอย่างกฎตรวจสอบ:
· รถขนผลผลิตออก แต่ไม่มีใบส่งของ/บัตรชั่งน้ำหนัก → สร้าง Case ระดับสูง
· ปุ๋ย/สารเคมีออกจากคลังช่วงที่กำหนด แต่ไม่มีใบเบิกอนุมัติ → แจ้ง Warehouse + Farm Manager สอบทาน
· ผลผลิตทั้งแปลงต่ำกว่าแผนมาก ทั้งที่รายงานงานภาคสนามครบตามแผน → ส่งตรวจความถูกต้องของข้อมูล
· เข้าพื้นที่จัดเก็บนอกเวลาทำการโดยไม่มีอนุมัติงาน → แจ้ง Compliance Officer พร้อมภาพเหตุการณ์
หลักการออกแบบ (Independent Assurance Layer): GAT ไม่ใช่ระบบปฏิบัติการแทน TNR และไม่อนุมัติรายการทางธุรกิจ — TNR Operations ทำงานจริง/แก้ไขข้อบกพร่อง · BMC TNR อนุมัติแผนแก้ไขตามอำนาจ · GAT ตรวจหลักฐาน ทดสอบการควบคุม ประเมินความเสี่ยง ให้ Assurance อย่างอิสระ · OAC รับรายงานประเด็นเกินอำนาจ BMC/ข้ามบริษัท
⚖️ SoD: ผู้ปฏิบัติงานไม่ควรยืนยันความถูกต้องงานตนเองเพียงลำพัง · ผู้ตรวจสอบไม่ควรเป็นเจ้าของการแก้ไขที่ตนต้องตรวจรับภายหลัง
ข้อจำกัด: กล้องวัด "การเคลื่อนไหว/การมีอยู่" ได้ แต่ยืนยันชนิด-คุณภาพ-น้ำหนักผลผลิตไม่ได้ (ต้องใช้เครื่องชั่ง/ใบชั่ง/ตรวจนับ) · ต้นทุน-กำไร-ภาษีต้องตรวจจาก ERP และเอกสารโดยตรง · การเชื่อมต่อจริงต้องตรวจสิทธิ์ API รูปแบบข้อมูล ความถี่ส่งข้อมูล การเก็บรักษาหลักฐาน และประวัติการเปลี่ยนแปลงก่อนพัฒนา

Workflow มาตรฐาน: เมื่อ CCTV พบความผิดปกติ

ปรับใช้ได้ทั้ง 6 ธุรกิจ — จาก Detect ถึง Close มีมนุษย์ยืนยันที่ปลายทางเสมอ

1Detect — ตรวจจับCCTV AI ตรวจพบเหตุการณ์ → VMS สร้าง Event ID พร้อม Camera ID, Timestamp, Event Type, ภาพ/คลิปอ้างอิง
2Validate — ตรวจคุณภาพEvent Gateway ตรวจแหล่งที่มา เวลา ส่งซ้ำ สิทธิ์ผู้ส่ง ก่อนส่งเข้าประมวลผล
3Correlate — เชื่อมโยงOpenClaw เรียก API ที่อนุญาต: ทะเบียนรถ · ใบสั่งซ่อม · การอนุมัติ · รายการเงิน · Access Log
4Evaluate — ประเมินเสี่ยงใช้กฎล่วงหน้า (รถออกไม่มีอนุมัติ ฯลฯ) · AI ช่วยสรุปและอธิบายความผิดปกติ
5Create Case — สร้างหลักฐานบันทึก Event ID, เวลา, สาขา, ระบบต้นทาง, กฎที่ผิดเงื่อนไข, ภาพอ้างอิง, ข้อมูลที่ใช้ตรวจสอบ ลง Case Register
6Notify — แจ้งแจ้งผู้จัดการสาขา/เจ้าของกระบวนการ/Compliance ตามระดับความเสี่ยง ผ่านช่องทางที่องค์กรอนุมัติ
7Verify & Close — ปิดเคสผู้รับผิดชอบยืนยันผล บันทึกการแก้ไข · GAT สุ่มตรวจ/ทบทวนเคสสำคัญก่อนนำเข้ารายงาน OAC/BMC

🇱🇦 สปป.ลาวกฎหมายข้อมูลอิเล็กทรอนิกส์และที่เกี่ยวข้องตรวจข้อกำหนดท้องถิ่น: ข้อมูลภาพ · ความลับ · การเก็บ/ส่งข้อมูลอิเล็กทรอนิกส์ · cross-border transfer — ให้ที่ปรึกษากฎหมายลาวยืนยันล่าสุดก่อนใช้ระบบจริง
🇰🇭 กัมพูชากฎหมาย/ข้อกำหนดข้อมูลที่มีผล ณ วันติดตั้งตรวจข้อกำหนด: ความลับทางธุรกิจ · กฎธุรกิจสินเชื่อ · ส่งข้อมูลข้ามประเทศ — ไม่ควรสันนิษฐานว่าใช้ข้อกำหนดเดียวกับไทย
หมายเหตุสถานะกฎหมาย (OECD): รายงานเผยแพร่ปี 2026 ระบุว่า ณ ธ.ค. 2025 กัมพูชาและลาวยังไม่มีกรอบกฎหมายคุ้มครองข้อมูลส่วนบุคคลเฉพาะที่เทียบเท่าบางประเทศอาเซียน · กัมพูชามีร่างปี 2025 ที่ยังไม่ประกาศใช้ในช่วงรายงานกล่าวถึง — ข้อมูลนี้ไม่ใช่ข้อยืนยันสถานะ ณ ต.ค. 2026 ต้องตรวจสอบกฎหมาย/ประกาศล่าสุดก่อนตัดสินใจ

มาตรฐานขั้นต่ำที่เสนอเป็นมาตรฐานกลางกลุ่มบริษัท

  • ป้ายแจ้ง CCTV + ประกาศวัตถุประสงค์เหมาะสมแต่ละพื้นที่
  • ทะเบียนกล้อง: วัตถุประสงค์ · ผู้มีสิทธิ์ดูภาพ · ระยะเวลาเก็บรักษา
  • นโยบายการใช้ AI วิเคราะห์ภาพ รวมถึงการห้ามใช้เกินวัตถุประสงค์
  • การควบคุมการส่งภาพ/ข้อมูลลูกค้าข้ามประเทศ
  • กระบวนการรับคำขอเข้าถึงข้อมูล + การระงับการลบหลักฐานเมื่อมีเหตุสอบสวนที่ชอบด้วยกฎหมาย (legal hold)
  • ประเมินผลกระทบด้านข้อมูลส่วนบุคคลและความปลอดภัยก่อนใช้งานจริง ตามความจำเป็นและข้อกฎหมาย

4.2 ข้อจำกัดทางเทคนิคและแนวทางควบคุม

ความเสี่ยงผลกระทบแนวทางควบคุม
ภาพย้อนแสง มืด บดบังตรวจจับผิด/พลาดปรับตำแหน่งกล้อง · ทดสอบหลายช่วงเวลา · วัด False Positive/Negative
อ่านป้ายทะเบียนผิดจับคู่รถผิดคันConfidence Threshold + ตรวจสอบกับข้อมูลทะเบียน/ภาพต้นฉบับ
นาฬิกากล้องไม่ตรงจับคู่ธุรกรรมผิดเวลาใช้ NTP + กำหนด Time Zone มาตรฐาน (งานแรก ๆ ของ PoC)
Event ซ้ำ / เครือข่ายขัดข้องแจ้งเตือนซ้ำ ข้อมูลหายEvent ID · Idempotency · Queue · Retry
AI สรุปผิดข้อสงสัยไร้มูลกฎที่ตรวจสอบซ้ำได้ + มนุษย์ยืนยันเสมอ
เข้าถึง Gateway เกินจำเป็นข้อมูลรั่ว / ระบบถูกสั่งงานมิชอบLeast Privilege · Secret Management · Network Segmentation · Audit Trail
ข้อความใน Event ไม่ปลอดภัยPrompt Injectionปฏิบัติต่อ Event/เอกสารเป็น "ข้อมูล" ไม่ใช่ "คำสั่ง" · จำกัดเครื่องมือ · ตรวจสอบสิทธิ์ด้วยโค้ด (Hooks บางประเภททำงานด้วยสิทธิ์ Gateway ไม่ใช่ sandbox — ตรวจโค้ดและจำกัดสิทธิ์ก่อนเปิดใช้)

ลำดับความสำคัญ PoC — เริ่มที่ธุรกิจใดก่อน

เหตุผลหลัก: กิจการรถยนต์มีเหตุการณ์ทางกายภาพตรวจจับชัด + มีข้อมูลตรวจสอบไขว้ง่าย (ทะเบียน/ใบสั่งซ่อม/อะไหล่/อนุมัติรถออก) จึงวัดผลง่ายกว่าความเสี่ยงการเงินเฉพาะทาง

P1ดีเลอร์อีซูซุและศูนย์บริการ ความเหมาะสมสูง
ตรวจรถเข้า-ออกเทียบ DMS · รถเข้าซ่อมเทียบ Job Order · ความผิดปกติเบิกอะไหล่ — วัดจำนวนเหตุการณ์ผิดปกติ เวลาตรวจสอบ และมูลค่าความสูญเสียที่ป้องกันได้
P2ศูนย์ซ่อมตัวถังและสี ต่อยอดจาก P1
รถค้างซ่อม · ความสอดคล้องอะไหล่-ใบสั่งซ่อม · รถส่งมอบและงานเคลม — นำ Event Gateway + Case Management จากโครงการแรกมาใช้ซ้ำ
P3ธุรกิจสินเชื่อ 3 ประเทศ ต้องเตรียมกฎหมายก่อน
เงินสด · เข้าถึงเอกสาร · ทำงานนอกเวลา · เชื่อมระบบสินเชื่อ+Compliance — มีประโยชน์ต่อการกำกับสูง แต่ต้องเตรียมข้อกำหนดกฎหมายและข้อมูลแต่ละประเทศ
P4บริษัทพัฒนาซอฟต์แวร์ เริ่มเร็วถ้า log พร้อม
เข้าห้อง Server · Change Ticket ↔ Access Log · เหตุการณ์ Security — เริ่มได้เร็วหากมี Access Log + Change Management ที่พร้อม
P5บริษัทลงทุนการเงินดิจิทัล ซับซ้อนสูงสุด
Transaction Monitoring · เข้าถึงระบบสำคัญ · เชื่อมหลักฐานกายภาพกับ Audit Trail — ต้องเน้นควบคุมสิทธิ์ ความปลอดภัย และข้อกำกับธุรกิจการเงิน
ข้อสังเกต: ลำดับนี้เป็นข้อเสนอเบื้องต้น ไม่ใช่ข้อสรุปว่า P1 มี ROI สูงสุดแน่นอน — ถ้าบริษัทซอฟต์แวร์มี Access Log พร้อมและต้องการลดความเสี่ยงห้อง Server เร่งด่วน อาจเริ่ม PoC ส่วนนั้นควบคู่ได้

Preconditions(1) รหัสแปลง รอบผลิต ชนิดพืช หน่วยนับมาตรฐาน (2) รายการเก็บเกี่ยว/เคลื่อนไหวคลังพร้อมเวลาและผู้บันทึก (3) ระบุ Source of Truth ของแต่ละข้อมูล (4) เกณฑ์ความคลาดเคลื่อนที่ได้รับอนุมัติ

  1. ดึงข้อมูลผลผลิตตามแปลงและรอบผลิตจาก Farm System
  2. ดึงยอดรับเข้า เบิกจ่าย ขาย ปรับปรุง และคงเหลือจาก ERP
  3. เทียบข้อมูลกับ Sheets และหลักฐานชั่งน้ำหนัก/ตรวจนับจริง
  4. คำนวณส่วนต่างทั้งจำนวน หน่วยนับ และมูลค่า
  5. จัดลำดับความเสี่ยงตามมูลค่า ความถี่ และลักษณะรายการ
  6. สร้าง Finding พร้อมหลักฐานและมอบหมายเจ้าของงานให้ตรวจสอบสาเหตุ
  7. GAT ตรวจสอบผลการกระทบยอดและสรุปสถานะปิดประเด็น
Exception Flow
  • หน่วยนับไม่ตรงกัน: หยุดสรุปผลอัตโนมัติและขออนุมัติ Conversion Factor
  • ข้อมูลไม่ครบ: แจ้ง Data Owner และจัดสถานะ Evidence Incomplete
  • ส่วนต่างสูง: แจ้ง Farm Manager และ BMC ตามเกณฑ์ Escalation
  • สัญญาณอาจเกี่ยวกับการทุจริต: เก็บรักษาหลักฐาน จำกัดการเข้าถึง ส่งตรวจตามกระบวนการที่อนุมัติ — ห้ามสรุปความผิดจากส่วนต่างเพียงอย่างเดียว
EvidenceHarvest Log · ใบชั่งน้ำหนัก · ใบรับเข้า/เบิกจ่าย · Stock Card · รายงานตรวจนับจริงและเอกสารปรับปรุงยอด · ERP/Farm System extracts พร้อมวันเวลาและผู้บันทึก · Log การเปลี่ยนแปลงและภาพ VMS เมื่อเกี่ยวข้อง
Risk / Controlความเสี่ยง: ผลผลิตสูญหาย บันทึกซ้ำ ตัดสต็อกไม่ถูกต้อง หรือปรับยอดโดยไม่มีอำนาจ
การควบคุม: Reconciliation อัตโนมัติ · Segregation of Duties · อนุมัติการปรับยอด · ตรวจนับแบบสุ่มโดยอิสระ
KPI
  • อัตรารายการที่กระทบยอดได้ = รายการที่ตรงตามเกณฑ์ ÷ รายการที่ตรวจทั้งหมด × 100
  • มูลค่า/จำนวนส่วนต่างที่ยังไม่อธิบาย
  • จำนวนการปรับยอดที่ไม่มีหลักฐานครบ
  • เวลาตั้งแต่พบส่วนต่างจนถึงการแก้ไข
Acceptance Criteria
  1. รายการที่เข้าเกณฑ์ทั้งหมดมีผลการกระทบยอดและสถานะชัดเจน
  2. ทุกส่วนต่างเกินเกณฑ์มี Case ID เจ้าของงาน กำหนดเสร็จ และหลักฐาน
  3. การปรับยอดต้องมีผู้อนุมัติและ Audit Trail
  4. GAT สุ่มย้อนกลับจากรายงานไปยังหลักฐานต้นทางได้

UC-02 · ตรวจสอบต้นทุนการเพาะปลูกและผลต่างงบประมาณ — Farm Cost Assurance P1 ▾

วัตถุประสงค์: ตรวจสอบต้นทุนตามแปลง รอบผลิต และชนิดพืช เพื่อค้นหาต้นทุนผิดปกติ การใช้วัสดุเกินมาตรฐาน และค่าใช้จ่ายที่ขาดหลักฐาน

ActorsGAT Auditor, Farm Manager, Procurement, Finance, BMC TNR
Triggerปิดเดือน ปิดรอบผลิต ต้นทุนเกินงบ หรือพบรายการใช้วัสดุ/ค่าแรงผิดปกติ
Preconditionsมีงบประมาณ/มาตรฐานต้นทุนที่อนุมัติแล้ว · กำหนดวิธีจัดสรรต้นทุนร่วม (เครื่องจักร น้ำ แรงงาน) · มีข้อมูลแปลง รอบผลิต ปริมาณผลผลิต และเอกสารค่าใช้จ่าย
Main Flow
  1. ดึงงบประมาณและมาตรฐานต้นทุนจาก ERP/Sheets
  2. ดึงข้อมูลปัจจัยการผลิตและกิจกรรมจาก Farm System
  3. จับคู่ปุ๋ย เมล็ดพันธุ์ สารป้องกันฯ ค่าแรง น้ำมัน ซ่อมบำรุง
  4. คำนวณต้นทุนจริงเทียบงบและต้นทุนต่อหน่วยผลผลิต
  5. ตรวจหาผลต่างสูง รายการซ้ำ และรายการไม่มีเอกสารรองรับ
  6. สร้าง Finding พร้อมผลกระทบทางการเงินและเจ้าของงาน
  7. GAT ตรวจหลักฐานและทดสอบการแก้ไขก่อนปิดประเด็น
Exception Flow
  • ไม่มีงบประมาณที่อนุมัติ: แสดง No Approved Baseline ห้ามสรุปว่าเกินงบ
  • ต้นทุนร่วมยังไม่จัดสรร: แยกเป็นรายการรอการจัดสรร ไม่สรุปเด็ดขาด
  • รายการซ้ำจากการนำเข้า: ตรวจเลขเอกสารและระบบต้นทางก่อนจัดเป็นข้อผิดพลาด
  • ต้นทุนเพิ่มจากภัยแล้ง/โรคพืช: ต้องมีหลักฐานเหตุผลและการอนุมัติ
Evidenceงบประมาณและ Cost Standard ที่อนุมัติ · ใบเบิกวัสดุ ใบสั่งซื้อ ใบรับของ ใบแจ้งหนี้ Payroll · รายงานกิจกรรมในแปลงและปริมาณผลผลิต · สูตรจัดสรรต้นทุนและ Audit Trail
Risk / Controlความเสี่ยง: ต้นทุนสูงผิดปกติ ค่าใช้จ่ายไม่จริง การจัดสรรต้นทุนบิดเบือน ใช้วัสดุโดยไม่บันทึก
การควบคุม: Budget-vs-Actual · Rate/Quantity Variance · อนุมัติค่าใช้จ่าย · แยกผู้ขอซื้อ ผู้รับของผู้บันทึกบัญชี
KPI
  • อัตราต้นทุนเกินงบตามเกณฑ์
  • ต้นทุนต่อหน่วยผลผลิตแยกตามแปลง/รอบผลิต
  • มูลค่ารายการไม่มีหลักฐานหรือรอคำอธิบาย
  • อัตราการปิด Finding ตามกำหนด
Acceptance Criteria
  1. รายงานแสดงต้นทุนจริง งบ ผลต่าง และเหตุผลที่บันทึก
  2. สูตรจัดสรรต้นทุนตรวจสอบย้อนหลังได้
  3. รายการเกินเกณฑ์ทุกกรณีมีผู้รับผิดชอบและหลักฐาน
  4. ไม่ปิด Finding เพียงเพราะคำอธิบายโดยไม่มีหลักฐานสนับสนุน

UC-03 · ตรวจสอบการจัดซื้อและคลังปัจจัยการผลิต — Procurement & Input Inventory P1 ▾

วัตถุประสงค์: ตรวจสอบความถูกต้องตั้งแต่การขอซื้อจนถึงการรับสินค้า จ่ายเงิน และนำไปใช้จริงในแปลง

ActorsGAT Auditor, Procurement, Warehouse, Finance, Farm Manager, BMC TNR
Triggerมีรายการจัดซื้อใหม่ การรับของ การจ่ายเงิน การเบิกวัสดุ หรือตรวจพบราคาผิดปกติ
Preconditionsมีทะเบียนผู้ขายและระดับอำนาจอนุมัติ · เอกสารขอซื้อ/สั่งซื้อ/รับของเชื่อมโยงกัน · หน่วยนับและราคาต่อหน่วยเปรียบเทียบกันได้
Main Flow
  1. ดึงใบขอซื้อ ใบสั่งซื้อ ใบรับของ ใบแจ้งหนี้ ข้อมูลชำระเงิน
  2. จับคู่เอกสารและตรวจผู้อนุมัติ
  3. เทียบราคา ปริมาณ เงื่อนไขกับประวัติ/ใบเสนอราคา
  4. ตรวจแบ่งซื้อ รายการซ้ำ ผู้ขายที่มีความสัมพันธ์/ผลประโยชน์ทับซ้อนตามสิทธิ์ที่เข้าถึง
  5. เทียบปริมาณเบิกกับกิจกรรมการผลิตใน Farm System
  6. สร้าง Finding สำหรับรายการผิดปกติ
  7. ติดตามคำชี้แจงและหลักฐานแก้ไข
Exception Flow
  • ไม่มีข้อมูลเทียบราคา: แสดง ต้องตรวจสอบด้วยหลักฐานเพิ่มเติม ไม่สรุปว่าแพงเกินควร
  • สินค้าทดแทนสเปกต่างกัน: เทียบสเปกและเงื่อนไขก่อน
  • เอกสารมาคนละรอบ: เข้าคิวตรวจตามระยะเวลา ไม่จัดเป็นทุจริตอัตโนมัติ
  • สงสัยแบ่งซื้อหนีอำนาจอนุมัติ: ตรวจรวมตามผู้ขาย ช่วงเวลา วัตถุประสงค์ + ทบทวนโดยผู้มีอำนาจ
EvidencePR · PO · Goods Receipt · Invoice · Payment Record · ใบเสนอราคา สเปก ทะเบียนผู้ขาย ประวัติอนุมัติ · ใบเบิกวัสดุและรายงานใช้จริง · Log การเปลี่ยนแปลงข้อมูลจัดซื้อ
Risk / Controlความเสี่ยง: จัดซื้อโดยไม่มีอำนาจ รับของไม่ครบ จ่ายซ้ำ ราคาผิดปกติ ผลประโยชน์ทับซ้อน
การควบคุม: Three-way matching · Approval Matrix · Duplicate Invoice Detection · Vendor Due Diligence · ผู้ตรวจนับรับของแยกจากผู้จัดซื้อ
KPI
  • สัดส่วนรายการจัดซื้อที่เอกสารครบ
  • จำนวน/มูลค่ารายการจับคู่เอกสารไม่ผ่าน
  • มูลค่ารายการชำระซ้ำที่ยืนยันแล้ว
  • อัตราการแก้ไขข้อยกเว้นตาม SLA
Acceptance Criteria
  1. ระบบเชื่อมโยงเลขอ้างอิงตั้งแต่ขอซื้อถึงจ่ายเงิน
  2. รายการเอกสารไม่ครบถูกแยกออกจากรายการที่ผ่านการตรวจ
  3. การแจ้งเตือนทุกรายการมีเหตุผลและหลักฐานอ้างอิง
  4. การเปลี่ยนผู้ขาย/ราคา/ปริมาณย้อนหลังมี Audit Trail

UC-04 · ตรวจสอบเครื่องจักร ทรัพย์สิน น้ำ และพลังงาน — Asset & Resource Assurance P2 ▾

วัตถุประสงค์: ลดความสูญเสียจากเครื่องจักร ทรัพย์สิน น้ำ เชื้อเพลิง และพลังงานที่ไม่มีการควบคุมเพียงพอ

ActorsGAT Auditor, Farm Manager, Asset/Maintenance Owner, Finance, IT/VMS, BMC TNR
Triggerปิดเดือน ตรวจนับสินทรัพย์ มีค่าใช้จ่ายซ่อมสูง หรือพบการใช้เชื้อเพลิง/พลังงานผิดปกติ
Preconditionsมีทะเบียนสินทรัพย์ หมายเลขประจำเครื่อง ผู้ดูแล · บันทึกชั่วโมงใช้งาน ซ่อมบำรุง เบิกเชื้อเพลิง · ข้อมูลค่าใช้จ่ายและใบอนุมัติที่เกี่ยวข้อง
Main Flow
  1. ดึงทะเบียนสินทรัพย์และประวัติการใช้งาน
  2. เทียบชั่วโมงใช้งานกับเชื้อเพลิง/ค่าไฟ/ค่าน้ำ
  3. ตรวจประวัติซ่อมบำรุงและค่าใช้จ่ายเทียบเกณฑ์
  4. เทียบผลตรวจนับจริงกับทะเบียนทรัพย์สิน
  5. ใช้ VMS สนับสนุนการตรวจเหตุในพื้นที่เก็บทรัพย์สินเมื่อจำเป็น
  6. สร้าง Finding กรณีทรัพย์สินไม่พบ ค่าใช้จ่ายผิดปกติ หลักฐานไม่ครบ
  7. ตรวจผลแก้ไขและรายงานผล
Exception Flow
  • ไม่มีมิเตอร์/ชั่วโมงใช้งาน: ระบุข้อจำกัดข้อมูล เสนอจัดทำ Baseline
  • เครื่องจักรใช้ต่างภารกิจ: แยกประเภทงานก่อนเทียบอัตราสิ้นเปลือง
  • มีการย้ายทรัพย์สิน: ตรวจเอกสารอนุมัติและประวัติโอนก่อนจัดเป็นสูญหาย
EvidenceFixed Asset Register · ใบเบิกน้ำมัน ใบซ่อม Meter Reading ใบอนุมัติ · รายงานตรวจนับทรัพย์สินและภาพ VMS · ERP Transaction และประวัติแก้ไขข้อมูล
Risk / Controlความเสี่ยง: ทรัพย์สินสูญหาย ใช้ผิดวัตถุประสงค์ เบิกเชื้อเพลิงเกินจริง บันทึกค่าใช้จ่ายผิด
การควบคุม: Asset Tagging · Periodic Physical Verification · Preventive Maintenance · กระทบยอดปริมาณใช้กับกิจกรรมจริง
KPI
  • อัตราความครบถ้วนของทะเบียนทรัพย์สิน
  • จำนวนทรัพย์สินตรวจนับไม่พบ/ข้อมูลไม่ตรง
  • ค่าใช้จ่ายซ่อมต่อชั่วโมงใช้งาน
  • อัตราทำ PM ตามกำหนด
Acceptance Criteria
  1. ทรัพย์สินในขอบเขตมีเจ้าของและสถานะชัดเจน
  2. รายการใช้ทรัพยากรผิดปกติมีเกณฑ์เปรียบเทียบที่อธิบายได้
  3. Finding มีหลักฐานต้นทางและผู้รับผิดชอบ
  4. ข้อจำกัดด้านข้อมูลถูกระบุในรายงาน ไม่ตีความเป็นผลผ่าน

UC-05 · ตรวจสอบเหตุการณ์ CCTV/VMS และ AI — Video Intelligence & Loss Prevention P1 ▾

วัตถุประสงค์: ใช้ข้อมูลกล้องช่วยตรวจสอบเหตุการณ์เสี่ยงในพื้นที่เกษตร คลังปัจจัยการผลิต จุดชั่งน้ำหนัก จุดรับส่งผลผลิต และพื้นที่เครื่องจักร

Actorsหลัก: GAT Auditor, VMS Administrator, ผู้รับผิดชอบพื้นที่ TNR · สนับสนุน: Farm Manager, Warehouse, BMC TNR · OAC รับทราบเมื่อผลกระทบสูง
TriggerAI พบบุคคล/ยานพาหนะในพื้นที่จำกัด · กิจกรรมเวลาไม่ปกติ · คลาดเคลื่อนสินค้าคงเหลือ/ปริมาณส่งมอบ · ได้รับแจ้งเหตุจากผู้ปฏิบัติงานหรือผู้ตรวจสอบ
Preconditionsระบุตำแหน่งกล้อง พื้นที่ เวลาที่บันทึกได้ · กำหนดสิทธิ์เข้าถึงภาพและนโยบายเก็บหลักฐาน · ซิงก์เวลา VMS กับระบบธุรกิจ · มีเกณฑ์แจ้งเตือนและผู้รับผิดชอบแต่ละประเภทเหตุ
Main Flow
  1. รับ Alert จาก VMS/AI หรือรับคำขอตรวจภาพจาก Finding
  2. ตรวจสถานะกล้อง ช่วงเวลาบันทึก และคุณภาพภาพ
  3. ผูกเหตุการณ์กับแปลง คลัง ใบเบิก ใบส่งของ หรือรายการใน ERP/Farm System
  4. ผู้มีสิทธิ์ตรวจภาพและระบุข้อเท็จจริงที่สังเกตได้

Exception Flow
  • กล้องขัดข้อง/ภาพขาดช่วง: แจ้ง IT/VMS จัดสถานะ Coverage Gap
  • AI แจ้งผิด: บันทึก False Positive เพื่อปรับกฎ/โมเดล
  • ระบุบุคคล/เหตุการณ์ไม่วางใจ: ไม่ระบุตัวผู้กระทำจากภาพไม่ชัด
  • เหตุอาจเกี่ยวข้องการกระทำผิด: จำกัดการเข้าถึง รักษาความสมบูรณ์หลักฐานก่อนแจ้งผู้มีอำนาจ
  • ภาพเกี่ยวกับข้อมูลส่วนบุคคล: ใช้เฉพาะวัตถุประสงค์ที่ชอบด้วยกฎหมาย จำกัดสิทธิ์ ตามนโยบายความเป็นส่วนตัว

การควบคุม: Role-Based Access · Time Synchronization · Retention Policy · Export Log · Evidence Integrity · Human Verification

  • เวลาเฉลี่ย Alert→รับทราบ
  • อัตรา False Positive
  • สัดส่วนเวลาทำงานของกล้องพื้นที่เสี่ยง

  2. เหตุที่นำไปสู่ Finding เชื่อมหลักฐานต้นฉบับและระบบธุรกิจได้
  3. ผู้ไม่มีสิทธิ์เปิด/ส่งออกภาพจำกัดสิทธิ์ไม่ได้

  5. มีรายงานกล้องขัดข้องและเหตุที่ตรวจไม่ได้

UC-06 · ตรวจสอบกฎหมาย ภาษี และ Compliance (LCT) — Legal, Tax & Compliance Assurance P1 ▾

วัตถุประสงค์: ให้ TNR มีทะเบียนหน้าที่ตามกฎหมายที่ใช้บังคับจริง ผู้รับผิดชอบ กำหนดเวลา และหลักฐานยืนยันการปฏิบัติตาม

Actorsหลัก: GAT LCT Reviewer, Finance/Tax Owner, Compliance Owner · สนับสนุน: Farm Manager, HR/Safety, BMC TNR · OAC รับทราบการละเมิดสำคัญ/เกินอำนาจบริษัท
Triggerใกล้กำหนดยื่นแบบ/ชำระภาษี/ต่ออายุใบอนุญาต/ส่งรายงาน · ปิดเดือน ไตรมาส ปี · เปลี่ยนกิจกรรมหรือข้อกำหนด · พบรายได้/ค่าใช้จ่ายหรือเอกสารไม่ตรงกัน

Main Flow
  1. โหลดทะเบียนหน้าที่ LCT และคำนวณวันครบกำหนด
  2. ตรวจผู้รับผิดชอบและสถานะงานแต่ละรายการ
  3. ดึงยอดขาย รายได้ ค่าใช้จ่าย บัญชีจาก ERP เทียบข้อมูลภาษี
  4. ตรวจความครบถ้วนใบกำกับภาษี ใบเสร็จ หลักฐานยื่น/ชำระ
  5. แจ้งเตือนงานใกล้ครบกำหนด ขาดหลักฐาน หรือมีความแตกต่าง
  6. ส่งรายการให้เจ้าของชี้แจงและแนบเอกสาร
  7. GAT ตรวจความครบถ้วนและความสอดคล้องของหลักฐาน
  8. ยกระดับรายการอาจผิดกฎหมาย/ล่าช้า/ผลกระทบสูงต่อ BMC/OAC
  9. ปิดรายการเมื่อหลักฐานเพียงพอและมีผู้ตรวจทาน
Exception Flow
  • ไม่แน่ใจกฎหมายใดใช้บังคับ: บันทึก Legal Applicability Review ให้ผู้เชี่ยวชาญยืนยัน
  • ERP ไม่ตรงกับรายงานภาษี: สร้าง Exception ตรวจกระทบยอด ห้ามแก้ข้อมูลต้นทางเพื่อให้ยอดตรงโดยไม่อนุมัติ
  • ใบอนุญาต/หลักฐานขาด: คงสถานะ Evidence Missing ไม่ถือว่าปฏิบัติแล้ว
  • ความเสี่ยงละเมิดผลกระทบสูง: แจ้ง BMC ยกระดับ OAC ทันที ไม่รอรอบเดือน
  • ข้อโต้แย้งการตีความกฎหมาย: ขอความเห็นผู้เชี่ยวชาญ ไม่ให้ AI ตัดสินเป็นข้อยุติ
EvidenceLegal/Compliance Register และแหล่งอ้างอิง · ใบอนุญาต หนังสืออนุมัติ เอกสารราชการ · ERP extracts, GL, Trial Balance, Invoice, Tax Filing, Payment Proof · บันทึกการตรวจทานและการอนุมัติ
Risk / Controlความเสี่ยง: ยื่น/ชำระภาษีผิดหรือช้า รายได้ไม่ตรง ใบอนุญาตหมดอายุ ไม่ปฏิบัติตามกฎหมาย
การควบคุม: Compliance Calendar · Deadline Alert · Tax Reconciliation · Evidence Checklist · Maker-Checker · ทบทวนโดยผู้เชี่ยวชาญ
KPI
  • จำนวนการละเมิด LCT ที่ยืนยันแล้ว (เป้าหมาย 0)
  • จำนวนหน้าที่ตามกฎหมายที่เกินกำหนด (เป้าหมาย 0)
  • อัตราหน้าที่ยืนยันว่าปฏิบัติครบมีหลักฐาน
  • จำนวนรายการรอการยืนยันข้อกฎหมาย
  • จำนวนความแตกต่างทางภาษีที่ยังไม่กระทบยอด
Acceptance Criteria
  1. หน้าที่ทุกข้อมีประเทศ/พื้นที่ แหล่งอ้างอิง เจ้าของ กำหนดเวลา
  2. แจ้งเตือนก่อนครบกำหนดตาม Lead Time ที่อนุมัติ
  3. เปลี่ยนสถานะเป็น Compliant ต้องมีหลักฐาน+ผู้ตรวจทาน
  4. ความแตกต่างทางบัญชี/ภาษีมี Case ID ติดตามได้
  5. รายงานแยก ยืนยันการละเมิด / สงสัยรอตรวจ / ข้อมูลไม่พอ ออกจากกัน
⚠️ การกำหนดกฎหมายที่ใช้บังคับกับ TNR ต้องอิงที่ตั้งจริงของกิจการ ชนิดพืช การใช้สารเคมี แหล่งน้ำ การจ้างงาน และกิจกรรมเชิงพาณิชย์ — เอกสารนี้เป็นกรอบควบคุม ไม่ใช่ข้อสรุปทางกฎหมายเฉพาะกรณี

UC-07 · ตรวจสอบการขาย การส่งมอบ และรับชำระเงิน — Sales-to-Cash Assurance P1 ▾

วัตถุประสงค์: ตรวจสอบความครบถ้วนของรายได้ ตั้งแต่คำสั่งขาย การชั่งน้ำหนัก ส่งมอบ ออกใบแจ้งหนี้ จนถึงการรับเงินและบันทึกบัญชี

  3. เทียบใบส่งของกับใบแจ้งหนี้และการบันทึกรายได้

  • มูลค่ารายได้ที่รอกระทบยอด
  • จำนวนส่วนลด/ใบลดหนี้ไม่มีหลักฐานอนุมัติ
  • อายุลูกหนี้เกินกำหนดตามเงื่อนไข

  1. รายการขายทุกชุดในขอบเขตเชื่อมกับเอกสารส่งมอบและบันทึกรายได้
  2. รายการมีส่วนต่างมีเหตุผล สถานะ ผู้รับผิดชอบ
  3. การแก้ไขราคา/ปริมาณย้อนหลังตรวจสอบได้
  4. รายงานแยกข้อผิดพลาดที่ยืนยันแล้วจากรายการรอคำอธิบาย

UC-08 · ตรวจสอบความถูกต้องของข้อมูลบัญชีและการปิดงวด — Financial Data Integrity P1 ▾

  1. ดึง Trial Balance, GL และรายงานจาก Farm System

  3. ตรวจรายการบันทึกด้วยมือ รายการปลายงวด JE ผิดปกติ
  4. ตรวจวันบันทึก วันที่เกิดรายการ และงวดบัญชี
  5. วิเคราะห์ยอดผิดปกติ/ไม่สอดคล้องกิจกรรมจริง
  6. สร้าง Exception และขอหลักฐาน

  • บันทึกบัญชีเป็นยอดรวม: ขอรายละเอียดประกอบและวิธีจัดสรร
  • JE หลังปิดงวด: ตรวจเหตุผลและอำนาจอนุมัติ
  • ไม่มีข้อมูลต้นทาง: จัดเป็นข้อจำกัดด้านหลักฐาน ไม่สรุปว่าไม่มีรายการจริง

Risk / Controlความเสี่ยง: รายได้/ต้นทุนผิดงวด สินทรัพย์/สินค้าคงเหลือน่าเชื่อถือลดลง รายงานการเงินไม่น่าเชื่อถือ

KPI

  • จำนวน JE ที่ขาดหลักฐาน
  • อัตราการปิดงวดตามกำหนด
  • รายการปรับปรุงหลังปิดงวดที่ไม่ได้รับอนุมัติตามเกณฑ์
Acceptance Criteria
  1. มีรายงานกระทบยอดระหว่างข้อมูลต้นทางกับบัญชี
  2. รายการปรับปรุงที่เข้าเกณฑ์มีหลักฐาน+ผู้อนุมัติ
  3. ข้อจำกัดข้อมูลและรายการยังไม่สรุปแสดงชัดเจน
  4. ย้อนกลับจากยอดรวมไปยังรายการต้นทางได้

Main Flow
  1. ดึงแผนผลิตและข้อมูลจริงจาก Farm System
  2. เทียบผลผลิตต่อพื้นที่และต้นทุนต่อหน่วยระหว่างแปลง/รอบที่เทียบกันได้
  3. ตรวจความเบี่ยงเบนการใช้น้ำ วัสดุ เวลาปฏิบัติงาน
  4. แยกเหตุอธิบายได้ (ภัยแล้ง โรคพืช เปลี่ยนแผน) จากรายการไม่มีคำอธิบายเพียงพอ
  5. สร้าง Risk Alert ให้ผู้รับผิดชอบตรวจสอบ
  6. GAT ตรวจว่ามีการวิเคราะห์สาเหตุและติดตามมาตรการเหมาะสม
  7. สรุปแนวโน้มและข้อจำกัดข้อมูลต่อ BMC
Exception Flow
  • ไม่มี Baseline: รายงาน ยังไม่มีเกณฑ์เปรียบเทียบ ไม่จัดเป็นความผิดปกติยืนยันแล้ว
  • พืชต่างชนิด/คนละระยะ: ไม่เทียบตรงหากไม่ปรับเกณฑ์
  • ข้อมูลอากาศ/พื้นที่ไม่ครบ: ระบุข้อจำกัดให้ผู้เชี่ยวชาญตรวจ
  • ผลผลิตต่ำจากเหตุธรรมชาติ: ตรวจหลักฐานและผลกระทบ ไม่สรุปเป็นความบกพร่องของบุคคลอัตโนมัติ
Evidenceแผนเพาะปลูก บันทึกกิจกรรม ผลผลิต พื้นที่ · ข้อมูลการใช้น้ำและปัจจัยการผลิต · รายงานโรคพืช/ภัยธรรมชาติหรือคำอธิบายผู้เชี่ยวชาญ · บันทึกวิเคราะห์สาเหตุและแผนปรับปรุง
Risk / Controlความเสี่ยง: รายงานผลผลิตไม่สะท้อนข้อเท็จจริง ใช้ทรัพยากรไม่มีประสิทธิภาพ ไม่แก้ไขสาเหตุผลผลิตต่ำ
การควบคุม: Benchmark เทียบเคียงได้ · Exception Monitoring · Root Cause Analysis · ทบทวนโดยผู้รู้ด้านเกษตรกรรม
KPI
  • ผลผลิตต่อพื้นที่เทียบกับแผน
  • ต้นทุนต่อหน่วยผลผลิต
  • อัตราสูญเสีย/ความเบี่ยงเบนการใช้ทรัพยากร
  • อัตรา Risk Alert ที่ตรวจและปิดตามกำหนด
Acceptance Criteria
  1. รายงานระบุ Baseline และสมมติฐานที่ใช้เปรียบเทียบ
  2. Alert ทุกกรณีมีเหตุผลและผู้รับผิดชอบ
  3. ไม่ใช้ความเบี่ยงเบนทางสถิติอย่างเดียวเป็นหลักฐานการกระทำผิด
  4. ผลวิเคราะห์สาเหตุและมาตรการแก้ไขย้อนหลังได้

UC-10 · บริหาร Audit Findings และ Corrective Actions — Audit Finding & Remediation Governance P1 ▾

วัตถุประสงค์: ทำให้ทุกข้อค้นพบมีระดับความเสี่ยง เจ้าของงาน แผนแก้ไข กำหนดเวลา และการตรวจยืนยันก่อนปิดประเด็น

Actorsหลัก: GAT Auditor, GAT Report Owner, Process Owner TNR · ผู้กำกับ: BMC TNR, OAC สำหรับกรณีเข้าเกณฑ์ยกระดับ
Triggerผลตรวจสอบไม่ผ่าน · ระบบพบรายการผิดปกติผ่านการยืนยันเบื้องต้น · งานแก้ไขใกล้/เกินกำหนด · พบปัญหาเดิมซ้ำหรือความเสี่ยงวิกฤต
Preconditionsมาตรฐานจัดระดับความเสี่ยง · เจ้าของกระบวนการและอำนาจอนุมัติแผนแก้ไข · ทะเบียน Findings รหัสไม่ซ้ำ · SLA และเงื่อนไขปิดประเด็น
Main Flow
  1. สร้าง Finding ID + รายละเอียด เกณฑ์อ้างอิง สภาพที่พบ หลักฐาน
  2. ระบุผลกระทบ ความเป็นไปได้ ระดับความเสี่ยง
  3. เจ้าของกระบวนการวิเคราะห์ Root Cause + ทำ Corrective Action Plan
  4. BMC อนุมัติแผน/ทรัพยากรตามระดับอำนาจ
  5. ติดตามสถานะ แจ้งเตือนก่อน/หลังครบกำหนด
  6. เจ้าของงานแนบหลักฐานผลการแก้ไข
  7. GAT ตรวจความเพียงพอและทดสอบการควบคุมหลังแก้ไข
  8. ปิดประเด็นเมื่อผ่านเกณฑ์ หรือเปิดกลับหากแก้ไขไม่เพียงพอ
  9. สรุปประเด็นคงค้างและความเสี่ยงต่อ BMC/OAC
Exception Flow
  • เจ้าของงานไม่เห็นด้วยกับ Finding: บันทึกคำชี้แจง+หลักฐาน ให้ผู้มีอำนาจทบทวน
  • แก้ไขเกินกำหนด: บันทึกเหตุผล ความเสี่ยงระหว่างรอ ยกระดับตาม SLA
  • หลักฐานไม่พอ: คงสถานะ Pending Verification
  • ปัญหาเกิดซ้ำ: ประเมิน Root Cause ยกระดับตามเกณฑ์
  • ผู้ตรวจสอบมีผลประโยชน์ทับซ้อน: เปลี่ยนผู้ตรวจยืนยันที่เป็นอิสระ
EvidenceAudit Finding · Criteria · Condition · Root Cause · Risk Rating · Corrective Action Plan ผู้รับผิดชอบ กำหนดเสร็จ การอนุมัติ · หลักฐานก่อน/หลังแก้ไขและผลทดสอบ · Log เปลี่ยนสถานะ/ขยายเวลา/ปิด-เปิดใหม่
Risk / Controlความเสี่ยง: ข้อค้นพบไม่ถูกแก้ไข ปิดงานไม่มีหลักฐาน ปัญหาเดิมเกิดซ้ำ
การควบคุม: Workflow บังคับกรอกข้อมูลสำคัญ · Maker-Checker · Escalation Matrix · แยกผู้แก้ไขออกจากผู้ตรวจรับ
KPI
  • Critical Findings ที่ยังเปิดอยู่
  • Corrective Actions เกินกำหนด
  • อัตราปิดประเด็นตาม SLA
  • อัตราการเกิดซ้ำของ Finding
  • สัดส่วนการปิดประเด็นมีหลักฐานผ่านการตรวจยืนยัน
Acceptance Criteria
  1. Finding ทุกข้อมี ID ระดับความเสี่ยง เจ้าของ กำหนดเวลา
  2. เปลี่ยนระดับ/ขยายกำหนดมีเหตุผล+Audit Trail
  3. เจ้าของงานปิด Finding ของตนเองโดยไม่ผ่าน GAT ไม่ได้
  4. Finding ที่ปิดแล้วต้องมีหลักฐาน+ผลทดสอบตามเกณฑ์
  5. รายงานประเด็นคงค้าง/เกิดซ้ำต่อ BMC/OAC ได้

UC-11 · Monthly Oversight Report สำหรับ BMC และ OAC — Monthly Oversight & Executive Escalation P1 ▾

วัตถุประสงค์: จัดทำรายงานที่แสดงสถานะความเสี่ยง ผลการตรวจสอบ และข้อบกพร่องสำคัญ โดยแยกข้อเท็จจริง ข้อสงสัย และข้อจำกัดของข้อมูลออกจากกัน

ActorsGAT Report Owner, GAT Auditor, BMC TNR, OAC, Process Owners
Triggerสิ้นสุดรอบรายงานรายเดือน หรือเกิดเหตุสำคัญที่ต้องรายงานทันที
Preconditionsรอบรายงานและวันปิดข้อมูล · KPI Definition และเกณฑ์ความเสี่ยงที่อนุมัติ · ข้อมูล Findings, Corrective Actions, LCT, Evidence และผลการตรวจสอบ
Main Flow
  1. รวบรวมข้อมูลจาก Use Case ทั้งหมด
  2. ตรวจความครบถ้วนและรายการยังไม่ยืนยัน
  3. คำนวณ KPI เทียบเดือนก่อน/เป้าหมาย
  4. จัดลำดับความเสี่ยงตามความรุนแรง ผลกระทบ ระยะเวลาคงค้าง
  5. สรุป Critical Findings, LCT Breaches, Overdue Actions, Evidence Gaps
  6. GAT Reviewer ตรวจความถูกต้องของรายงาน
  7. ส่งรายงาน BMC และยกระดับ OAC ตามเกณฑ์
  8. บันทึกการตัดสินใจ ข้อสั่งการ เจ้าของ กำหนดเสร็จ
  9. ติดตามมติเข้าสู่รอบรายงานถัดไป
Exception Flow
  • ข้อมูลไม่ครบตามกำหนด: รายงาน Incomplete Data พร้อมแหล่งข้อมูลและผลกระทบ
  • KPI ไม่มี Baseline: ไม่แสดงว่าเป็นผลผ่าน/ไม่ผ่านโดยไม่มีเกณฑ์
  • เหตุวิกฤตระหว่างเดือน: ส่ง Escalation ทันทีตามนโยบาย ไม่รอสิ้นเดือน
  • BMC/OAC ขอข้อมูลเพิ่ม: บันทึกคำขอ เจ้าของ วันตอบกลับ
EvidenceMonthly Oversight Report + KPI Calculation · Source Data Snapshot และวันที่ดึงข้อมูล · รายการ Findings/Corrective Actions · รายงานประชุม/มติและหลักฐานติดตามข้อสั่งการ
Risk / Controlความเสี่ยง: รายงานไม่ครบ ข้อมูลผิด/ซ้ำ ประเด็นสำคัญถูกซ่อน ผู้บริหารตัดสินใจบนข้อมูลไม่น่าเชื่อถือ
การควบคุม: Data Quality Checks · Report Review · Version Control · Source Traceability · Escalation Policy
KPI
  • รายงานส่งตรงเวลา
  • สัดส่วน KPI ที่มีแหล่งข้อมูลย้อนกลับได้
  • จำนวนประเด็นวิกฤตที่ไม่ได้รายงานตามเกณฑ์
  • อัตราดำเนินการตามมติ BMC/OAC ภายในกำหนด
Acceptance Criteria
  1. รายงานระบุช่วงข้อมูล วันที่ดึงข้อมูล ข้อจำกัดชัดเจน
  2. ตัวเลขสำคัญย้อนกลับไปยังแหล่งข้อมูลต้นทางได้
  3. แยกยืนยันแล้ว/รอตรวจสอบ/ข้อมูลไม่เพียงพอ
  4. มีหลักฐานการทบทวนและส่งรายงาน
  5. ประเด็นที่ต้องตัดสินใจมีผู้รับผิดชอบ+เวลาติดตาม

กติกากลางของระบบ GAT (ใช้ร่วมกันทุก Use Case)

15.1 สถานะของรายการ

สถานะความหมาย
New Alertระบบหรือผู้ตรวจพบสัญญาณผิดปกติ ยังไม่ยืนยันข้อเท็จจริง
Under Reviewอยู่ระหว่างตรวจสอบหลักฐาน
Evidence Incompleteหลักฐานไม่ครบหรือไม่สามารถตรวจยืนยันได้
Confirmed Findingมีหลักฐานเพียงพอรองรับข้อค้นพบ
Action Plannedมีแผนแก้ไขและผู้รับผิดชอบแล้ว
Remediation in Progressอยู่ระหว่างดำเนินการแก้ไข
Pending Verificationผู้รับผิดชอบแจ้งว่าแก้ไขแล้ว แต่ GAT ยังไม่ตรวจยืนยัน
Closed — VerifiedGAT ตรวจหลักฐานและยืนยันการแก้ไขตามเกณฑ์
Reopenedพบว่าการแก้ไขไม่เพียงพอหรือเกิดปัญหาซ้ำ
ข้อกำหนด: ห้ามนับ New Alert หรือข้อสงสัยที่ยังไม่มีหลักฐานเพียงพอเป็นการละเมิดที่ยืนยันแล้ว

15.2 การจัดระดับความเสี่ยง

ระดับเกณฑ์ตัวอย่างการดำเนินการ
Criticalอาจเกิดผลกระทบร้ายแรงหรือเร่งด่วนต่อกิจการ กฎหมาย หรือทรัพย์สินแจ้งผู้มีอำนาจทันที รักษาหลักฐาน จัดทำแผนควบคุมเร่งด่วน
Highผลกระทบสำคัญ มีโอกาสเกิดซ้ำ หรือการควบคุมหลักล้มเหลวให้ BMC กำกับแผนแก้ไขและติดตามถี่ขึ้น
Mediumความบกพร่องผลกระทบจำกัดแต่ควรแก้ไขดำเนินการตาม SLA ที่กำหนด
Lowข้อสังเกตหรือโอกาสปรับปรุงบันทึกและติดตามตามรอบที่เหมาะสม

ระดับความเสี่ยงต้องพิจารณาความรุนแรง โอกาสเกิด ความสามารถในการตรวจพบ และผลกระทบจริง — ไม่ใช้มูลค่าเงินเพียงตัวเดียว

15.3 กติกา Evidence — หลักฐานทุกชิ้นควรมีอย่างน้อย

  • Evidence ID และ Finding ID ที่เกี่ยวข้อง
  • ระบบต้นทาง ผู้สร้าง/ผู้ส่งออก และวันเวลาที่ดึงข้อมูล
  • ช่วงเวลาที่ข้อมูลครอบคลุม
  • ผู้เข้าถึงหรือแก้ไขหลักฐาน และประวัติการเปลี่ยนแปลง
  • สถานะความครบถ้วนและข้อจำกัด
  • สิทธิ์การเข้าถึงและระยะเวลาเก็บรักษาตามนโยบาย

หลักฐานจาก CCTV ควรมี Camera ID, Timestamp และบันทึกการส่งออกภาพ · ข้อมูลทางการเงินควรมีเลขอ้างอิงเอกสารและระบบต้นทาง

Acceptance Criteria ระดับระบบ (System Acceptance Checklist)

ใช้ตัดสินว่าระบบ GAT รุ่นนำร่องพร้อมส่งมอบหรือยัง ไม่ใช่เพียงว่าหน้าจอเปิดใช้งานได้

✓เกณฑ์

AC-06 — ผู้ปฏิบัติงานไม่สามารถปิด Finding ของตนเองโดยไม่มีการตรวจยืนยันตามอำนาจ

AC-10 — ทดสอบกรณีข้อมูลขาดหาย ข้อมูลซ้ำ การเชื่อมต่อขัดข้อง และสิทธิ์ไม่เพียงพอแล้ว

  • Asset & VMS: เหตุการณ์เสี่ยง กล้องขัดข้อง และสถานะการตรวจสอบ
  • LCT: หน้าที่ตามกฎหมาย กำหนดเวลา หลักฐาน และสถานะ
  • Findings: ระดับความเสี่ยง อายุประเด็น และการเกิดซ้ำ
  • Governance: เจ้าของงาน กำหนดเสร็จ และมติ BMC/OAC ที่ยังค้าง

ตัวเลข 0 ในสองช่อง LCT เป็นค่าเป้าหมาย ไม่ใช่ผลการตรวจสอบจริง · ช่องขีดหมายถึงยังไม่มีข้อมูลที่ยืนยันได้

แผนดำเนินการ 90 วัน (TNR)

ระยะงานหลักผลส่งมอบ
วัน 1–30สำรวจกระบวนการ TNR, ข้อมูลต้นทาง, Risk & Control Matrix, Legal Register และสิทธิ์การเข้าถึงScope, Data Map, Risk Register, KPI Dictionary
วัน 31–60ทดลอง UC-01, UC-02, UC-03, UC-06 และ UC-10 พร้อมเชื่อมข้อมูลที่จำเป็นDashboard รุ่นนำร่อง, Findings Register, LCT Calendar, Action Workflow
วัน 61–90เพิ่ม UC-05/UC-07/UC-08 ตามความพร้อม ทดสอบข้อมูลและสิทธิ์ จัดทำรายงานให้ BMC/OACUAT Results, Monthly Oversight Report, Remediation Plan และข้อเสนอขยายผล

การเลือก Use Case ในช่วงวัน 31–60 ควรยืนยันจากความเสี่ยงจริงและความพร้อมของข้อมูลก่อน · CCTV/AI ควรเริ่มเฉพาะจุดเสี่ยงที่ระบุชัด ไม่จำเป็นต้องนำทุกกล้องเข้าระบบพร้อมกัน
