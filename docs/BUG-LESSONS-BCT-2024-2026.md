## 4. Lessons → มาตรการออกแบบ Web PP7

### LESSON 1 — สูตรลูกโซ่ใน Google Sheet คือต้นเหตุที่กำเริบ (หมวด 1+6+10 ≈ 29.5%)
- **ที่เจอ:** #N/A, ข้อมูลไม่ขึ้น, ดึงไม่ได้, รายงานไม่มา — และพังลูกโซ่ข้ามไฟล์ (bug สมาชิกซ้ำใน pkgmember → เพี้ยนไปทุกไฟล์ที่อ้างอิง)
- **ต้นเหตุ:** ข้อมูลอ้างอิงชีตลูกโซ่ (IMPORTRANGE/VLOOKUP) พังทันทีเมื่อเปลี่ยนชื่อชีต/คอลัมน์/แถว และไม่มี data contract ร่วมกัน
- **Web PP7:**
  - ตารางข้อมูลต้นทางเดียว (single source of truth) + อ่าน/เขียนผ่าน API (GAS backend) — ไม่พึ่งสูตรลูกโซ่
  - Schema ตารางเป็นทางการ + มี versioning — เปลี่ยนโครงสร้างต้อง migration + test ก่อนขึ้นจริง
  - รายงาน/dashboard ทุกหน้าคำนวณจากข้อมูลต้นทางเดียว — ไม่มี "สรุปสองชุด" เทียบกันไม่ตรง
  - Health Check รายวัน (cron): validate ความครบถ้วน + ตรวจ key ซ้ำ + anomaly → เตือนทีมก่อนผู้ใช้เจอ

### LESSON 2 — แจ้งเตือนอัตโนมัติต้องอ่านสถานะ "ณ เวลาส่ง" (11.6%)
- **ที่เจอ:** แจ้งเตือนบอกผิด (ซ่อมบำรุงแล้วระบบบอกยังไม่ได้ทำ, ลงเวลาแล้วแจ้งวันหาย), ส่งไม่ครบ, แจ้งซ้ำเดิมทุกวัน
- **ต้นเหตุ:** Script แจ้งเตือนอ่านสถานะไม่ตรงจุด ไม่มี log ไม่มีกลไกกันส่งซ้ำ
- **Web PP7:**
  - ทุกแจ้งเตือนดึง state สดจาก DB ณ ตอนส่งเสมอ — ห้าม cache สถานะข้ามรอบ
  - notification_log: ส่งอะไร ให้ใคร เมื่อไร ผลอะไร — ตรวจย้อนหลัง/retry ได้
  - idempotency key กันแจ้งซ้ำ + retry schedule กรณีส่งไม่สำเร็จ
  - หน้า "ประวัติการแจ้งเตือน" ให้แอดมิน/ผู้บริหารเห็นสถานะการแจ้งทั้งหมดแบบเรียลไทม์

### LESSON 3 — แก้ไข/ลบข้อมูลต้องให้ผู้ใช้ทำเองตามกติกา (11.6%)
- **ที่เจอ:** "รบกวนแก้ไข/ลบให้หน่อย" + ชีท + แถว เป็นงานประจำของแอดมินกว่า 300 เคส
- **ต้นเหตุ:** ระบบเดิมไม่มี edit/delete flow และไม่มี ownership ของข้อมูล
- **Web PP7:**
  - ทุกโมดูลมี Edit/Delete ตามสิทธิ์ RBAC (admin/hr_manager/bu_manager/employee) — ไม่ต้องรอแอดมิน
  - Soft delete + audit trail — ห้าม hard delete เสี่ยงหายถาวร
  - ผูกกับ OKR Obj.3 KR1 (Self-Service ≥ 90%) — หมวดนี้ต้องลูกหมัด

### LESSON 4 — เวลาทำงาน/ใบลา ต้องเป็น transaction เดียว (8.9%)
- **ที่เจอ:** ลงเวลาแล้วแจ้งวันหาย, อนุมัติใบลาแล้วสคริปยังแจ้งหาย (สองพื้นที่ข้อมูลไม่ sync กัน)
- **ต้นเหตุ:** ข้อมูลลงเวลา/ใบลาถูกพุชข้ามหลายชีทแยกกัน → sync ตกหล่น/race condition
- **Web PP7:**
  - Event เวลา/ใบลาเป็น transaction เดียว มี status เดียว (pending→confirmed/approved) — ไม่มี sync ระหว่างสองแหล่ง
  - สถานะต้องเห็นได้ทันทีที่ผู้ใช้ทำ (ผู้ใช้ต้องเห็น "ทำเรียบร้อย" จริง)
  - ทุก event มี source of truth + timestamp + ผู้ทำ

### LESSON 5 — กระแสเงินต้อง reconcile ได้ (8.4%)
- **ที่เจอ:** เคลมแล้วไม่เข้ากระเป๋า, ยอด BCT vs statement ต่างกัน, ส่วนต่างสะสม 54,000 LP ตรวจจับไม่ได้เป็นสัปดาห์, CEW อนุมัติแล้วโอนไม่ครบ
- **ต้นเหตุ:** มี 2 แหล่งข้อมูลเงินแยกกัน (รายงานการโอน vs statement จริง) ไม่มีกระบวนการ reconcile
- **Web PP7:**
  - เงิน/แรงจูงใจทุกตัว (P6): one-write principle — เหตุการณ์เงินบันทึกครั้งเดียวเป็น transaction log
  - มีรายงาน reconcile เทียบยอดสองฝั่งอัตโนมัติ + alert ทันทีที่เจอส่วนต่าง — ไม่ให้สะสม
  - ยอดรวมทุกยอดคำนวณจาก log ณ บ้านที่เดียว — ไม่มี "ยอดรวมคนละที่"

### LESSON 6 — สิทธิ์เข้าถึงตั้งจากฐานสมาชิกอัตโนมัติ (4.0%)
- **ที่เจอ:** อีเมล 3 ตัวลืม whitelist, ฟอร์มติดสิทธิ์เปิดไม่ได้, tier ผิด, ลงทะเบียน TG ซ้ำ
- **ต้นเหตุ:** whitelist manual ทีละอีเมล → ลืมเป็นเรื่องปกติ
- **Web PP7:**
  - RBAC จากฐานข้อมูลสมาชิกอัตโนมัติ (role ผูกกับตำแหน่ง/บทบาทองค์กร) — ไม่แมนนวล whitelist ทีละคน
  - Provisioning สมาชิกใหม่ → สิทธิ์อัตโนมัติตาม role ทันที

### LESSON 7 — กันข้อมูลซ้ำตั้งแต่ปากทางเข้า (ในหมวด 1)
- **ที่เจอ:** ไฟล์ pkgmember มี id + ชื่อ-นามสกุลซ้ำกัน → เพี้ยนไปทุกไฟล์ที่อ้างอิง
- **ต้นเหตุ:** ไม่มี unique key + validation ณ จุดบันทึก
- **Web PP7:** Unique key + validation ณ ฟอร์มทุกโมดูล — block ค่าซ้ำก่อน save เสมอ

### LESSON 8 — Bug ต้องจบด้วย "ต้นเหตุ — แก้ที่ราก ไม่ใช่ที่เคส" (บทเรียนรวม)
25 เดือน 3,007 ticket แต่ความถี่ไม่ลด = โครงสร้างไม่เปลี่ยน → นี่คือ reason หลักที่ Web PP7 ต้องเปลี่ยนทั้งสถาปัตยกรรม (API + DB + RBAC) ไม่ใช่สร้างหน้าตาใหม่ทับ Google Sheet เดิม

## 5. ข้อสังเกตเชิงกระบวนการ (สำคัญไม่แพ้เทคนิค)

1. **การแจ้งเป็นข้อความแชตอิสระ** — 34% อธิบายไม่ชัดพอจะจัดหมวดอัตโนมัติ → ทีม fix ต้องตามถามเพิ่มทุกครั้ง ใช้เวลา key เก้อรอ
2. **ลิงก์ย่อ + ชีต Restricted** — สิทธิ์ไม่ครบ ผู้แก้เปิดดูไม่ได้ เสียเวลาขอสิทธิ์เป็นขั้นตอน
3. **ไม่มี SLA ที่มองเห็นได้** — ไม่มีหน้าจอบอกว่า ticket ไหนรอนานแค่ไหน ผู้บริหารไม่เห็นภาพความเดือด
4. **แช่งตั๋วเดียวปลายทางไม่ชัด** — แจ้ง #bug ทุกอย่าง ทั้ง bug จริง, คำขอแก้ข้อมูล, คำถาม, คำขอฟีเจอร์ → จัดคิวไม่ได้

→ แนวทาง Web PP7: **ฟอร์มแจ้งปัญหาในระบบ** (ให้เลือกประเภท + แนบชีท/หน้าจอที่พบ + เก็บ context อัตโนมัติ) — ระบบจัดหมวดที่อย่างน้อย 90% อ่านเข้าใจได้

## 6. Definition of Done สำหรับทุกหน้า/ฟังก์ชัน Web PP7

ทุกหน้า/ฟังก์ชันถือว่า "เสร็จ" เมื่อผ่านครบ:

- [ ] **V1 — Validation ณ Input:** กันค่าว่าง/ซ้ำ/รูปแบบผิดก่อน save ทุกฟิลด์
- [ ] **V2 — Data Source เดียว:** สรุป/รายงานคำนวณจากข้อมูลต้นทางเดียว ไม่มีสูตรลูกโซ่ข้ามชีต
- [ ] **V3 — Audit Log:** ทุก write (สร้าง/แก้/ลบ) เก็บ who/what/when/before/after — ตาม OKR Obj.1 KR3 (Audit Log ครบ 100%)
- [ ] **V4 — Self-Service:** Edit/Delete ผู้ใช้ทำเองตาม RBAC + Soft delete
- [ ] **V5 — State ทันที:** สถานะของทุกการทำงานเห็นได้ทันที ณ ที่ทำ (ไม่ต้องรอดึงข้อมูล)
- [ ] **V6 — Notification เป็นระบบ:** อ่าน state สด + idempotent + log + ทดสอบกันแจ้งซ้ำ/ไม่ส่งก่อน deploy
- [ ] **V7 — Reconcile เงิน:** ยอดเงิน/รางวัลคำนวณจาก transaction log + มีรายงานเทียบส่วนต่าง + alert
- [ ] **V8 — Health Check รายวัน:** cron validate ตารางหลัก + key ซ้ำ + anomaly → เตือนทีมก่อนผู้ใช้เจอ
